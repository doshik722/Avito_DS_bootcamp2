# Кандидатогенерация объявлений услуг Авито

Итоговый Recall@50 на платформе — **0.841578**. Файл ответа: [`answer_catboost_lightgbm_top300.csv`](answer_catboost_lightgbm_top300.csv). Код для его воспроизведения — [`predict.py`](predict.py); ход экспериментов и их выводы сохранены в [`pipeline.ipynb`](pipeline.ipynb).

## Данные и проверка качества

`train.parquet` содержит 497 673 положительные пары «запрос — выбранное объявление», `benchmark_queries.parquet` — 2 452 запроса, `benchmark_items.parquet` — корпус из 189 212 объявлений. Поиск ведётся только в корпусе объявлений соответствующей выборки. Исторические клики train служат разметкой для Recall@50 и обучения моделей, но не подставляются в ответ как готовые `item_id`.

Использованы текст запроса, заголовок и описание объявления — для лексической и смысловой близости; текстовые фильтры и параметры — для сопоставления вида услуги; локации и координаты — потому что услугу часто выбирают поблизости. Цена, рейтинг, число отзывов, категории, флаг доставки, доступность связи и признаки пропусков переданы ранжировщикам: их влияние может зависеть от запроса, поэтому прямой фиксированный бонус не навязывается. Для E5 взяты исходные тексты, для лексического поиска — нижний регистр, `ё → е`, удаление пунктуации и служебных подписей вроде «вид услуги». Пропущенный текст заменён пустой строкой, числовые пропуски не превращались в нули без отдельного индикатора.

Качество до отправки считалось по Recall@50: для каждого запроса доля выбранных объявлений в 50 кандидатах, затем среднее по запросам. Валидация — 20% *текстов* `search_query` (67 186 запросов): одинаковые формулировки не попадают одновременно в train и validation. Для позднего подбора ранжировщиков взяты 4 500 запросов с разными текстами, разделённые на 3 000 обучающих и 1 500 проверочных. Кроме конечного Recall@50 измерялась *полнота пула* — сколько релевантных объявлений есть среди кандидатов до выбора 50; это верхняя граница качества, а не сама метрика.

## Гипотеза 1. Несколько лексических источников лучше одного

На всём каталоге проверены 12 сочетаний word TF-IDF, char TF-IDF (символьные 3–5-граммы) и BM25 с заголовком, описанием и фильтрами. Лучшие одиночные Recall@50: **0.1738** у BM25 «запрос → заголовок + описание», **0.1713** у char TF-IDF «запрос → заголовок», **0.1575** у BM25 по заголовку и **0.1493** у word TF-IDF по заголовку. Добавление фильтров прямо к тексту запроса ухудшило все три метода; описание помогло BM25, но мешало char TF-IDF.

После грубой и мелкой сетки весов текстовый скор стал

```text
T = 0.55·BM25(заголовок + описание)
  + 0.40·char-TF-IDF(заголовок)
  + 0.05·BM25(заголовок)
  + 0.00·word-TF-IDF(заголовок).
```

Каждый скор до сложения делится на свой максимум **внутри запроса**. Word TF-IDF с нулевым весом оставлен как источник кандидатов и признак модели. Подбор поднял Recall@50 с **0.1776** при равных весах до **0.1955**.

## Гипотеза 2. Локация и глубина поиска важнее малой разницы текстовых скоров

Сначала проверена формула `T + a·1[локации совпали]`; лучший проверенный бонус `a = 1` поднял Recall@50 **0.1955 → 0.5522** на коротком пуле. Затем увеличивалась глубина каждого текстового источника:

| Top-K источника | Полнота объединённого пула | Recall@50 с локацией |
| ---: | ---: | ---: |
| 500 | 0.6470 | 0.5522 |
| 1 000 | 0.7472 | 0.6306 |
| 3 000 | 0.8558 | 0.7079 |
| 5 000 | 0.8861 | 0.7238 |

Значит, многие ошибки возникали ещё *до* ранжирования: нужного объявления не было в коротком пуле. Финальный поиск сохраняет top-5 000 от каждого лексического источника.

## Гипотеза 3. Фильтры полезнее как отдельный сигнал - бонус общему скору

Правило «не менее 90% слов фильтра запроса есть в параметрах объявления» сохраняло только **89.91%** реально выбранных объявлений у запросов с фильтрами. Поэтому вместо удаления остальных введён индикатор

```text
F(q, i) = 1[|слова_фильтра(q) ∩ слова_параметров(i)| / |слова_фильтра(q)| ≥ 0.90].
```

Отдельный BM25 «фильтр → параметры объявления» поднял полноту текстового пула на запросах с фильтрами **0.8782 → 0.9322**. Однако при совместном подборе лучший *прямой* вес этого BM25 стал нулём: его кандидаты и признаки остались, а к итоговому скору добавляется `γ·F`. Ранний лучший `γ = 0.35` улучшил Recall@50 **0.7238 → 0.7350**; после изменения пула коэффициент перепроверен и в финале равен **0.55**.

Прямые прибавки `0.2·рейтинг` и `0.01·число отзывов` ухудшили Recall@50 до **0.6792** и **0.0087** соответственно. При переборе их коэффициентов лучшим оказался ноль; сами рейтинг, отзывы и флаги пропусков сохранены как признаки ранжировщиков. Ранний CatBoost на 17 признаках тоже уступил формуле (**0.7482 против 0.7606**), поэтому сначала расширялся пул кандидатов.

## Гипотеза 4. Смысловой поиск найдёт объявления без общего словаря с запросом

Для запроса с префиксом `query:` и заголовка с описанием с префиксом `passage:` посчитаны векторы [`intfloat/multilingual-e5-base`](https://huggingface.co/intfloat/multilingual-e5-base); ближайшие объявления ищутся локальным FAISS HNSW по косинусной близости. E5 отдельно давала Recall@50 **0.1968**, но её top-5 000 имел полноту **0.8402**. Объединение с текстовым пулом подняло его полноту **0.8861 → 0.9263**: найдено **3 496** дополнительных релевантных пар. Только добавление кандидатов улучшило прежнюю формулу **0.7566 → 0.7669**; добавление нормированной косинусной близости с весом **0.05** — до **0.7734**. Большие веса ухудшали результат.

## Гипотеза 5. География — не только точное совпадение ID

Центр локации оценён медианой координат объявлений. Для запроса с известным городом гео-сигнал равен `G_city = 1` в том же городе, `0.55` на расстоянии до 25 км, `0.25` на расстоянии 25–75 км, иначе `0`. Для локации запроса без городского центра связь с городом объявления оценена по положительным парам train:

```text
G_region(r, c) = log(1 + clicks(r, c)) / log(1 + max_city clicks(r, city)).
```

Точное совпадение ID давало Recall@50 **0.7735**, статическая шкала расстояний — **0.7910**, обученный региональный сигнал — **0.8204**, их сочетание — **0.8349**. После расширения пула коэффициенты подбирались заново: финальные множители составили **1.50** для `G_city` и **0.75** для `G_region`. Это не интерпретация числовых `location_id` как расстояния; геометрия берётся из координат, региональные связи — из кликов.

## Гипотеза 6. Искать текст ещё раз внутри подходящей географии

Глобальный BM25 может не включить подходящее объявление в top-5 000, даже если в радиусе 75 км оно высоко. Локальный BM25 среди объявлений соседних городов или городов, связанных с регионом, добавил **1 869** релевантных объявлений при top-3 000 и поднял полноту большого пула **0.9482 → 0.9658**. В том же эксперименте топ-3 000 и вес локального сигнала 0.05 улучшили фактический Recall@50 **0.8416 → 0.8463**; top-5 000 не помог. Локальный поиск только среди объявлений с совпадающим фильтром добавил всего 150 релевантных и не вошёл в финальный путь.

Формула смешивания локального и глобального поиска: `B = 0.95·norm(S) + 0.05·norm(local_BM25)`, где `S` включает текст, E5, географию и фильтр. Пул объединяется по уникальным объявлениям, поэтому один `item_id` не занимает несколько мест.

## Гипотеза 7. Перенести историю кликов и категории напрямую

Из 344 825 объявлений train с benchmark-каталогом пересекаются лишь **18 142**. Исторически выбранное объявление присутствует в benchmark для **366/2 452** запросов. Принудительный перенос истории на отдельной проверке дал Recall@50 **0.0102**; BM25 по накопленным запросам объявления добавил к текущему пулу 268 релевантных (**+0.0021** к полноте). Поэтому история не подставляется в финальные 50 напрямую.

Проверен также бонус на основе соответствия `search_category → item_category_id`. В положительных парах все четыре категории запроса в основном соответствовали одной категории объявления `114`; перебор коэффициента не менял Recall@50 **0.7734**. Категории оставлены признаками моделей, но не самостоятельным бонусом.

## Гипотеза 8. Обучить ранжировщик на первых кандидатах гибрида

CatBoostRanker с YetiRank получает top-300 прежнего скора и **44 признака**: скоры и позиции источников, E5, географию и координаты, совпадение фильтра, категорию и микрокатегорию, цену, рейтинг, отзывы, доступность связи, длины текстов и пересечение слов. Выбранные по запросу объявления имеют метку 1, остальные кандидаты той же группы — 0. Это позволяет модели учитывать взаимодействия признаков, не перебирая вручную отдельный коэффициент для каждого.

| Модель на одной проверке из 1 500 запросов | Recall@50 |
| --- | ---: |
| Исходная формула | 0.7984 |
| CatBoost, 30 признаков, top-100 | 0.8180 |
| CatBoost, 30 признаков, top-300 | 0.8256 |
| CatBoost, 44 признака, top-300 | 0.8320 |

Лучший вес CatBoost — **0.70** после нормализации скора внутри запроса. Далее на тех же 44 признаках проверен LightGBM с LambdaRank: на отложенных 1 500 запросах добавление 200 деревьев с весом **0.40** улучшило Recall@50 **0.832696 → 0.840274**. Проверка top-500 повысила полноту кандидатов, но ухудшила конечный Recall@50 до **0.836941** без переобучения и **0.835141** после него. Оставлен top-300. После выбора параметров обе модели обучены на всех 4 500 запросах; у LightGBM использованы 4 109 групп, где в top-300 был положительный пример.

## Финальная формула и ответ

Все текстовые скоры и E5-косинус делятся на максимум своего источника для данного запроса; отсутствующий в источнике кандидат получает ноль. Для кандидата `i` запроса `q`:

```text
G(q,i) = 1.50·G_city(q,i), если у запроса есть городской центр;
       = 0.75·G_region(q,i), если он определяется как регион;
       = 0 в остальных случаях.

S(q,i) = T(q,i) + 0.05·E5(q,i) + G(q,i) + 0.55·F(q,i)

B(q,i) = 0.95·[S(q,i) / max_j S(q,j)]
       + 0.05·[local_BM25(q,i) / max_j local_BM25(q,j)]

C(q,i) = 0.30·B(q,i) + 0.70·minmax_q(CatBoost(q,i))
R(q,i) = 0.60·C(q,i) + 0.40·minmax_q(LightGBM(q,i)).
```

Максимум по `j` берётся среди кандидатов данного запроса. `minmax_q` применяется отдельно к 300 кандидатам; если разброс нулевой, возвращает нули. Деление на нулевой максимум в остальных слагаемых также заменяется нулём. В общий пул входят четыре текстовых top-5 000, E5 top-5 000, BM25 по параметрам для запросов с фильтром и локальный географический BM25 top-3 000. По `B` оставляются 300, по `R` — 50 уникальных `item_id`.

## Обнаруженные ошибки и внешняя проверка

| Тип ошибки                                                                       | Что изменено |
|----------------------------------------------------------------------------------| --- |
| Текст релевантного объявления отсутствует в коротком текстовом top-K для запроса | Увеличена глубина; добавлены E5 и локальный BM25. |
| Близкое объявление в соседнем городе или региональный запрос без точного города  | Введены расстояние и связь «регион → город». |
| Жёсткий фильтр ошибочно удаляет выбранное объявление                             | Фильтр стал бонусом, не отсечением. |
| Сырые рейтинг и отзывы подавляют текстовый скор; есть пропуски                   | Убраны прямые бонусы, скоры нормализованы, пропуски переданы отдельными признаками. |

Разница между validation и скрытым benchmark совместима со сдвигом распределений, но сама по себе его не доказывает. Коэффициенты выбирались по validation; платформа использовалась для внешней проверки готовых вариантов.

## Воспроизведение

Поместите три исходных Parquet в `data/` (они не распространяются вместе с репозиторием). Проверено с Python 3.12. Готовые модели и поисковые массивы подготовлены для Git/Git LFS; промежуточные эксперименты исключены через [`.gitignore`](.gitignore).

Быстрый запуск финального решения:

```bash
python -m pip install -r requirements.txt
git lfs install
git lfs pull
python predict.py
```

Скрипт создаёт `answer.csv` и проверяет формат, существование и уникальность всех `item_id`. `python predict.py --verify` сравнивает выдачу с проверенным CSV: с готовыми артефактами локально получено полное совпадение. При отсутствии отдельных массивов они пересчитываются; при отсутствии ранжировщиков запускается [`train.py`](train.py). Для пересчёта E5 нужны локальные веса из Git LFS; полный пересчёт на CPU значительно дольше и из-за приближённого поиска/обучения не обязан дать побитово тот же CSV.

Полный запуск исследования: откройте [`pipeline.ipynb`](pipeline.ipynb) и выполните **Run All** из чистого ядра после установки зависимостей и подготовки `data/`. При успешном последовательном выполнении ноутбук создаст в корне проекта все семь CSV, отправлявшихся на платформу: `answer.csv`, `answer_location_filter.csv`, `answer_geo_e5_mixed.csv`, `answer_geo_local_mixed.csv`, `answer_geo_local_catboost_top300.csv`, `answer_geo_local_catboost_extra_all4500.csv` и последним — **`answer_catboost_lightgbm_top300.csv`**. Именно последний файл содержит лучший ответ; `answer.csv` при запуске ноутбука — ранний базовый вариант. Полный эксперимент включает длительные расчёты и может занять много часов.

Финальный код разделён по назначению: [`data.py`](avito_candidates/data.py) — данные, [`retrieval.py`](avito_candidates/retrieval.py) — BM25/TF-IDF/E5, [`signals.py`](avito_candidates/signals.py) — география и фильтры, [`features.py`](avito_candidates/features.py) — признаки моделей, [`pipeline.py`](avito_candidates/pipeline.py) — ранжирование и CSV. Использованы локальные open-source `scikit-learn`, `scipy`, `sentence-transformers`, `faiss-cpu`, `CatBoost` и `LightGBM`; версии указаны в [`requirements.txt`](requirements.txt). Внешние API при предсказании не используются.
